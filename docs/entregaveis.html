0. Visão geral

Cidadão beneficiado: pessoas com deficiência ou mobilidade reduzida, idosos, gestantes e quem circula com carrinho de bebê.

Problema: elas não sabem com antecedência se um local público tem rampa, banheiro acessível, elevador funcionando ou se está lotado. Barreiras (calçada quebrada, rampa bloqueada) não chegam a quem pode resolvê-las, e chuva forte deixa trajetos perigosos.

Solução: o app mostra a acessibilidade de cada local (recursos e obstáculos), a ocupação estimada por sensores e alertas de chuva intensa. O cidadão relata barreiras e acompanha o andamento; o administrador (prefeitura/zeladoria) prioriza e atualiza os relatos.

1. Banco de dados 2 pts

Modelo relacional em Oracle com 8 entidades, PK, FK, UNIQUE e CHECK, na 3ª forma normal: listas (recursos/obstáculos) ficam em tabela própria, o nível de ocupação é derivado (não armazenado) e o valor do alerta vem da leitura que o disparou.

Diagrama Entidade-Relacionamento

{{DER}}
RelacionamentoCardinalidadeRegra
USUARIO – OCORRENCIA1 : NCada relato tem um autor.
LOCAL – OCORRENCIA1 : NCada relato é sobre um local existente.
USUARIO – PREFERENCIA1 : 1PK da preferência é a FK do usuário (ON DELETE CASCADE).
LOCAL – ITEM_ACESSIBILIDADE1 : NRecursos e obstáculos (tp_item RECURSO/OBSTACULO).
LOCAL – SENSOR1 : NUNIQUE (tp_sensor, id_local): um sensor de cada tipo por local.
SENSOR – LEITURA_SENSOR1 : NHistórico de leituras, marcadas como simuladas.
LEITURA_SENSOR – ALERTA1 : 0..1UNIQUE (id_leitura): uma leitura dispara no máximo um alerta.

Script database/citizentech.sql

Remove as tabelas TB_CT_* (bloco PL/SQL, pode rodar várias vezes), cria as 8 tabelas com GENERATED BY DEFAULT AS IDENTITY, PK, FK, UNIQUE e CHECK (ex.: st_ocorrencia IN ('RECEBIDA','EM_ANALISE','ENCAMINHADA','RESOLVIDA'), LENGTH(ds_descricao) >= 12, vl_leitura >= 0), 3 índices e a carga inicial: 3 usuários (senhas em hash BCrypt), 4 locais, 15 itens, 4 relatos, 5 sensores, 8 leituras e 3 alertas.

5. Segurança 2 pts

Login seguro

Senhas armazenadas com BCrypt (salt aleatório, custo 10) em ds_senha_hash; nunca em texto puro. O login devolve um JWT HMAC-SHA256 com expiração de 2 h; mensagem de erro genérica (não revela se o e-mail existe).

Controle de acesso

PerfilPode
CIDADAOConsultar locais e alertas; criar relatos; ver/cancelar só os próprios relatos; editar só as próprias preferências.
ADMINTudo do cidadão + CRUD de locais, alterar status/excluir qualquer relato, encerrar alertas, painel de sensores.
DEVICE (sensor)Somente POST /sensores/leituras, autenticado pelo cabeçalho X-Device-Key.

Regras de rota no SecurityConfig (hasRole) + regras de “dono do recurso” nos services. O cadastro público sempre cria CIDADAO (não aceita perfil no corpo, evitando escalada de privilégio).

Boas práticas

PráticaImplementação
Validação de entradaBean Validation em todos os DTOs (tamanho, e-mail, senha forte, slug, faixa de valores) + CHECK no banco.
Proteção contra SQL injectionSomente JPA/JPQL com parâmetros vinculados; nenhuma concatenação de SQL (teste CT-21).
Proteção contra XSSTextos livres rejeitam < e >; respostas JSON; cabeçalho Content-Security-Policy, X-Content-Type-Options e X-Frame-Options DENY.
CriptografiaHash BCrypt das senhas e assinatura HMAC-SHA256 dos tokens; comparação da chave do dispositivo em tempo constante.
Força brutaBloqueio de 15 min após 5 senhas erradas para o mesmo e-mail (HTTP 429).
Segredos e errosSegredo JWT, chave IoT e senha do Oracle por variável de ambiente; respostas de erro sem stack trace.
CORS e sessãoCORS só para origens configuradas; API stateless (sem cookie de sessão).
PrivacidadeOcupação é contagem agregada (sem câmera nem identificação); alertas marcados como simulados.

6. Simulação de IoT 2 pts

O script iot/simulador_sensores.py lê iot/sensores.json e envia leituras em lote para a API a cada N segundos, autenticado como dispositivo. Cenários: normal, tempestade, lotacao, pico.

SensorO que medeLimiteComo influencia o sistema
OCUP-BIB-01, OCUP-TER-01, OCUP-CUL-01Contagem agregada de pessoas no local (sensor de passagem)35 / 60 / 40 pessoasAtualiza a ocupação e o nível (Baixa/Moderada/Alta) do local no app; acima do limite gera alerta “com alta ocupação”, sugerindo outro horário.
CHUVA-CUL-01, CHUVA-TER-01Pluviômetro: intensidade de chuva (mm/h)30 mm/hAcima do limite gera alerta de Clima: calçadas e rampas podem estar escorregadias ou alagadas.

Uso dos dados (regras na API)

1) Toda leitura é gravada em TB_CT_LEITURA_SENSOR. 2) Leitura ≥ limite cria alerta ATIVO (substitui o anterior do mesmo sensor). 3) Leitura abaixo do limite encerra o alerta ativo (situação normalizada). 4) Leituras com mais de 30 min marcam o local como “leitura desatualizada”. 5) Os alertas aparecem na aba Alertas do app.

7. Como executar

Passo a passo completo no README.md. Resumo:

# 1) API (Java 17 + Maven) - sobe com banco H2 em modo Oracle ja carregado
cd api
mvn spring-boot:run                     # Swagger: http://localhost:8080/swagger-ui.html

# 1b) Oracle FIAP: rode database/citizentech.sql no SQL Developer e depois
set ORACLE_USER=rmXXXXX & set ORACLE_PASSWORD=******
mvn spring-boot:run -Dspring-boot.run.profiles=oracle

# 2) Testes automatizados
mvn test

# 3) Sensores IoT (outro terminal)
python iot/simulador_sensores.py --cenario tempestade

# 4) App: abrir a raiz do projeto no Android Studio e rodar no emulador
#    (a URL padrao http://10.0.2.2:8080/api/ aponta para a API no PC)
